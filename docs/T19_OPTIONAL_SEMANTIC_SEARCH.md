# T19 — 선택형 경량 임베딩 의미 검색

## 관리자에서 정확도를 높이고 사용자 실행은 가볍게

- **제작용 LLM(T18)**: 큰 GGUF 또는 로컬 고성능 모델 서버를 사용해 원문 기반 예상 질문/용어를 사전 생성합니다. 이 모델은 Client에 포함하지 않습니다.
- **제작용 임베딩(T19)**: 선택한 *경량 임베딩 GGUF*로 원본 청크의 벡터를 **관리자 PC에서** 계산해 DB에 저장합니다. 제작은 시간이 오래 걸려도 괜찮습니다.
- **사용자 임베딩(T19)**: 의미 검색을 사용하도록 체크한 경우에만 **동일한 임베딩 GGUF** 및 `llama-embedding.exe`를 사용자 ZIP에 포함합니다. 질문 한 개만 인코딩하고 미리 저장한 문서 벡터와 비교합니다.
- **사용자 답변 모델(T16)**: 기존 Qwen3 1.7B 또는 선택한 소형 생성용 GGUF는 임베딩 모델·제작용 LLM과 독립적입니다.

```text
관리자(고성능)
PDF → OCR/구조 추출 → 원문청크 ──────────────┬───────┐
  ├─ 대형 제작용 LLM → 검색 질문/용어 → FTS5     │       │
  └─ 경량 임베딩 모델 → 청크벡터 → DB 저장 ─────┘       │
                                                     ▼
사용자(경량): 질문 → FTS5 (+ 선택형 임베딩 질문 인코더) → 원문 근거 → 소형 GGUF 답변
```

**임베딩 질문 인코더가 추가되는 점은 피할 수 없습니다.** 제작 PC에서 청크 벡터만 만들고 사용자에게 모델을 전혀 전달하지 않는다면 새로운 질문을 같은 벡터 공간에 표현할 수 없기 때문입니다. 사용자가 적은 질문을 이해하는 진정한 의미 검색을 하려면 호환되는 작은 인코더가 필요합니다.

## 관리자 GUI

1. 원본문서 폴더를 선택하고 필요하면 **PDF 레이아웃 보존 추출** 및 **스캔 PDF OCR**을 켭니다.
2. 필요하면 **제작용 AI로 문서 검색 표현 보강**을 켜고 큰 제작 모델을 지정합니다.
3. **의미 검색용 문서 벡터 생성**을 켠 뒤 임베딩 전용 GGUF를 선택합니다. 이 모델은 질문 측에서도 사용하므로 **가벼운 다국어 임베딩 GGUF**를 권장합니다. `llama-embedding.exe`는 자동 기본 경로를 사용하거나 별도 같은 계열 실행 파일을 선택합니다.
4. 선택한 임베딩 모델의 학습 규약에 따라 **generic** 또는 **e5** 프로필을 지정합니다. E5는 문서에 `passage: `, 질문에 `query: ` 접두어를 붙입니다.
5. **DB 재생성**을 실행합니다. 품질 보고서의 `embedding_index.complete: true`를 확인합니다. 모델의 SHA-256과 벡터 차원이 DB에 기록됩니다.
6. **사용자 패키지 제작**에서 **경량 의미 검색 모델 포함**을 켜고 동일한 GGUF를 선택합니다. DB와 파일 해시가 다르면 패키징을 거부합니다. 기본 유사도 기준은 0.72입니다.

기본 사용자 ZIP은 이 옵션을 켜지 않으면 임베딩 GGUF와 `llama-embedding.exe`를 포함하지 않고, **배포용 DB 복사본에서 사용하지 않는 문서 벡터 테이블도 제거·압축**합니다. 따라서 FTS5 + 소형 답변 모델만으로 실행하며, 관리자가 만든 원본 DB에는 벡터가 그대로 남습니다. 의미 검색을 선택하면 원본 벡터를 보존하고 동일 임베딩 GGUF를 함께 포장합니다.

## 검증된 한국어 경량 모델 (T21)

Windows CPU 통합 시험에서 다음 **실제 GGUF 모델과 llama.cpp v0.8.0**의 실행 호환성을 확인했습니다.

- 모델: [TwinSunsLLC/multilingual-e5-small-gguf](https://huggingface.co/TwinSunsLLC/multilingual-e5-small-gguf), 파일 `multilingual-e5-small-q8_0.gguf` (약 132 MB, MIT)
- 검증된 Git 리비전: `b6cac96`
- 모델 SHA-256: `e011debc1208e31bf7b6aebee2d9fc8bd2ca11694a77ed66ac9d0c9d0a877c93`
- 설정: 임베딩 프로필 **`e5`** (문서 `passage: `, 질문 `query: `), mean pooling, 384차원
- 실제 CI 측정: 합성 문서 청크 3개에 대한 제작용 벡터 생성까지 6.44초, 질문의 임베딩 검색 2.00초, 원문 출처 검색 성공
- 테스트: [T21 Windows CPU 실모델 테스트](https://github.com/danhk0612/DK-Knowledge-Engine/actions/runs/42586024500)

이 결과는 **모델 로딩, DB 구축, 한국어 질문 인코딩 및 원문 검색 동작**의 검증입니다. 고객 PDF의 검색 정답률이나 대량 문서에서의 성능을 입증하지 않습니다.

`cstr/multilingual-e5-small-GGUF`의 특정 변환본은 현재 v0.8.0 환경에서 BERT 토큰 유형 메타데이터 부족으로 로딩에 실패했습니다. 모델 이름만 같아도 GGUF 변환본끼리 호환성을 가정하지 말고, **배포할 정확한 파일을 관리자와 사용자에서 동일하게** 사용해야 합니다.

## 개발자 CLI

```powershell
python -m builder.knowledge_builder --source "D:\Manuals" `
  --database "D:\Knowledge\knowledge.db" --rebuild `
  --embedding-runtime "D:\llama\llama-embedding.exe" `
  --embedding-model "D:\models\multilingual-embedding.gguf" `
  --embedding-profile generic --embedding-gpu-layers 0
```

`--embedding-max-chunks 20`은 성능 시험용 일부만 인코딩합니다. **인덱스가 불완전하면 사용자 패키징의 의미 검색 옵션을 허용하지 않습니다.**

## 성능·정확도 한계

- 모든 문서 벡터는 `float32`로 DB에 저장되며, Client는 추가 Python 머신러닝 프레임워크·Torch·NumPy·Docker를 설치하지 않습니다.
- 사용자 측 임베딩 실행 파일은 질문마다 소형 GGUF를 로딩하고 종료합니다. **대기 중인 메모리 사용량은 낮지만 첫 질문과 각 질문의 처리 지연은 늘어날 수 있습니다.**
- 현 구현은 SQLite 범위 내 해당 제품/버전 벡터를 순차 비교하는 방식입니다. 문서가 수만 청크 이상이면 벡터 검색 지연이 증가하며 ANN 인덱스/서버는 포함하지 않습니다.
- `min_similarity` 값은 의미상 정답률의 보증이 아닙니다. 기본 0.72는 출발점이며 고객 문서별 정답 질문·오탐 질문으로 임계값을 평가해야 합니다.
- GGUF라 하더라도 **현 엔진의 llama.cpp v0.8.0 임베딩 실행 파일에서 지원하는 아키텍처**여야 합니다. 모델 제공자의 사용·재배포 라이선스를 확인해야 합니다.
- 고객 문서 추출 문제(OCR 누락, 표 순서 오류)는 임베딩만으로 해결되지 않습니다. `knowledge.quality.json`의 추출 결과를 우선 검토하세요.
- 초기 모델 동작과 실제 벡터 출력은 선택한 인코더 모델에 따라 달라지므로 합성 벡터 테스트만으로 모델 품질이 증명되지는 않습니다.

## 테스트 방법

같은 `knowledge.db`로 Client 의미 검색 옵션을 **켠 경우와 끈 경우**를 비교하고, 사용자가 실제로 할 법한 동일한 질문 세트를 사용하세요. 검증 기준은 원본문서 출처 Recall@5, 근거 정확성, 오답/미응답, CPU·메모리·질문별 지연입니다.
